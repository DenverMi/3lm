**From:** Itsuo Sakai
**To:** Hitomi Ohira , Jun Wang

アルプスアルパイン大平様アリオンのBluetooth認証担当の酒井です。いつもお世話になっております。

認証登録に関して新しいスレッドで送信させていただきます。

7/1に登録サイトが変更になったため、ご依頼のHM26の登録可能性を私のQuaificationWorkspace

の仮Projectで先行確認したした。その結果、下記2点の懸念点が発生しましたので御社関係者でのご検討をお願いします。

(1) Power Claasに関しての懸念点見積依頼書には Class2 と記載されていますので、下記の赤字の送信出力を想定されてるものと思います。

<BR/EDR>

Class 1: 100 mW（+20 dBm）≧ 送信出力 > 2.5 mW（+4 dBm）

Class 2: 2.5 mW（+4 dBm） ≧ 送信出力 > 0.25 mW（0 dBm）

Class 3: 1 mW　（0 dBm）　≧ 送信出力

<BLE>

Class 1 : 100 mW（+20 dBm）≧ 送信出力 ＞ 10 mW （+10 dBm）

Class 1.5: 10 mW（+10 dBm）≧ 送信出力 ＞ 2.5 mW（+4 dBm）

Class 2 : 2.5 mW（+4 dBm） ≧ 送信出力 ＞ 1 mW　（0 dBm）

Class 3 : 1 mW （0 dBm） ≧ 送信出力 ≧ 0.01mW（-20 dBm）

そして実機でRF(Class 2)、RF PHY(非Class 1)のICS内容で試験を実施し、レポートをエビデンスとし、Q社のD054625(QDID:[ID] /BB, LMP, LL, HCI, 4.0HCIのComponent登録)と組み合わせて

RF, RF PHY, LL, BB, LMP, HCI, 4.0HCIの階層を包含する旧Controller Subsystemの登録をご希望されているものと理解しております。

ここでQ社のD054625に問題があります。それはLL ICSの9/11がSupport YESで登録されています。

このためRH PHY 1/15(Class 1)をYESにしないと下記Invalidが出て登録ができません。

If [RFPHY] is Supported and [RFPHY] (1/15) is Not Supported then [LL] (9/11) is Excluded

今回の旧Controller Subsystemの登録で無理やりLL ICS 9/11をNOに変更することはできないことはありませんが、7/1以降の新登録サイトではLLの現行規定(TCRL [ID])に従って730項目の試験要求が発生します。BBの試験はBQTFでSIG指定テスターでの試験が規定されていますが、現時点でこのテスターを所有するBQTFは中国に1社あるのみ、かつこの項目数の試験費用と所要日数は想像がつきません。

回避策は①)Q社のD054625(QDID:[ID])の実装が優先でしたらRF PHYはClass 1で試験・登録するか、

②RF PHYがClass 2であることが優先でしたらQ社のD054625(QDID:[ID])代替のLL ICS 9/11:NOで登録された代替のCntrollerスタックを選定してください。

(2) 旧Controller Substsemの登録形態に関する懸念点今回のご依頼はRF, RF PHY試験を実施し、それをエビデンスとして旧Controller Substsem相当の登録を行い、その後御社でこの新規登録に旧Host Subsystem相当のホストスタック＋プロファイルを組み合わせて旧End Product相当の製品登録を行うことと理解しております。

ところが2024/6/30までのLaunch StudioではConsistency Check対象外であった組み合わせ指定の

Controller Subsystem、Host Subsystem、Profile Subsystem、End Product(＋Profile Subsystem)

が7/1以降はConsistency Check対象となりました。これにより前述の(1)の懸念点を解消後に旧

Controller Subsystem相当の登録を弊社責任でInvalid=0で登録できますが、次の段階で御社が実施する旧Host Subsystem相当のホストスタック＋プロファイルを組み合わせて旧End Product相当の製品登録の際にInvalid=0で登録できるかどうかは事前にシュミレーションできず、やってみないと分かりません。

そこで提案ですが、今回はRFとRF PHYだけの試験を実施して御社の製品登録の時点でRFとRF PHY

のレポートをエビデンスとして(1)の検証結果に応じたQ社のD054625またはその代替の登録および、

ホストスタック＋プロファイルを組み合わせて旧End Product相当の製品登録を行う流れをお勧めします。理由は旧Controller Subsystem相当の登録を弊社サポートでInvalid=0で登録できますが、

やってみないと分からない次の御社登録の段階で旧Controller Subsystem相当の登録の利用価値が無かったというリスクを回避できます。さらに7/1以降の登録は、旧Componet登録を参照した製品登録にに関するTCW(Test Case Waiver)がすでに出ていて、今回Componentを参照した中間的な部分階層(Core Controller)登録後にはComponent登録ではないこの登録を参照した製品登録ではこのTCW

が適用されない反面、御社の製品登録でRF,RF PHYレポートをエビデンスにしてQ社のD054625またはその代替のComponent登録、その他を参照すると当該TCWでInvalidの一部が救済される可能性が高いことが挙げられます。

以上Power Classの件と旧Controller Subsytem登録の是非の件をご検討ください。

(1) Power Claasに関しての懸念点見積依頼書には Class2 と記載されていますので、下記の赤字の送信出力を想定されてるものと思います。

<BR/EDR>

このためRH PHY 1/15(Class 1)をYESにしないと下記Invalidが出て登録ができません。

If [RFPHY] is Supported and [RFPHY] (1/15) is Not Supported then [LL] (9/11) is Excluded

今回の旧Controller Subsystemの登録で無理やりLL ICS 9/11をNOに変更することはできないことはありませんが、7/1以降の新登録サイトではLLの現行規定(TCRL [ID])に従って 730項目の試験要求が発生します。BBの試験はBQTFでSIG指定テスターでの試験が規定されていますが、現時点でこのテスターを所有するBQTFは中国に1社あるのみ、かつこの項目数の試験費用と所要日数は想像がつきません。

Controller Subsystem、Host Subsystem、Profile Subsystem、End Product(＋Profile Subsystem)

ホストスタック＋プロファイルを組み合わせて旧End Product相当の製品登録を行う流れをお勧めします。理由は旧Controller Subsystem相当の登録を弊社サポートでInvalid=0で登録できますが、
